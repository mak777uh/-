# Машинный контур лаборатории

Этот каталог — не публикация и не отчёт. Это **control plane** для агентов и
инструментов: маленький, текстовый, версионируемый слой, который отвечает на
вопросы «что сейчас идёт», «что уже закрыто», «какие артефакты считать
каноническими» и «можно ли безопасно занять эксперимент».

Человеческая интерпретация остаётся в [`../reports/`](../reports/README.md),
[`../articles/`](../articles/README.md) и [`../library/`](../library/README.md).
Сырые результаты — в `morphogenesis/experiments/`, веса — в
`morphogenesis/checkpoints/` (в git не попадают).

## Порядок чтения

Агент читает в таком порядке:

1. [`../AGENTS.md`](../AGENTS.md) — правила, команды, границы.
2. [`state.json`](state.json) — текущая фаза, активные прогоны, блокеры.
3. [`registry.json`](registry.json) — карта экспериментов и их артефактов.
4. [`runs/`](runs/) — манифесты конкретных прогонов.
5. `morphogenesis/experiments/` — сырые JSON-артефакты.
6. `../reports/` — человеческая интерпретация; не источник чисел.

## Научный цикл

Машинный контур хранит не только факты, но и ход работы. В `registry.json` есть
два поля, которые описывают цикл целиком:

- `program.loop` — восемь стадий: работа с источниками в публикациях → просмотр
  наших данных и статей → наша проверяемая гипотеза → проверка → отчёт и статья →
  обновление README (строка журнала экспериментов) → вклад в рукопись
  (`manuscript/`) → работа с источниками и новая гипотеза. Для каждой стадии
  указано, где она живёт (`where`) и что получается на выходе (`output`).
- `program.next_hypotheses` — очередь гипотез лаборатории: `id`, утверждение,
  способ проверки, статус (`planned` / `running` / `confirmed` / `rejected` /
  `blocked`), откуда взята.

У каждого закрытого эксперимента, у которого есть статья, — свой список
`next_hypotheses`: что проверять дальше после этого результата. Правило
«хороший научный результат закрывается статьёй и следующими гипотезами»
описано в [`../AGENTS.md`](../AGENTS.md) §3a.

`python scripts/lab.py validate` проверяет это машинно и падает, если:

- `program.loop` пуст или в нём нет обязательных стадий;
- `program.next_hypotheses` пуст, у гипотезы нет `statement` или `test`, или
  `status` не из допустимых;
- у эксперимента со статьёй нет `next_hypotheses`;
- журнал экспериментов в корневом `README.md` (между `<!-- ledger:start -->` и
  `<!-- ledger:end -->`) не покрывает все `experiment_id` из registry, содержит
  неизвестные или повторные id, либо русская метка статуса расходится с
  `status` (`закрыто` / `идёт` / `план` / `заблокировано` / `не запускался`);
- карта рукописи в `manuscript/README.md` (между `<!-- map:start -->` и
  `<!-- map:end -->`) не покрывает закрытые эксперименты со статьёй, ссылается на
  неизвестный id, оставляет раздел пустым или ставит статус вклада вне
  `внесено` / `частично` / `ожидает`; нет `manuscript/paper.md`,
  `manuscript/CHANGELOG.md` или `manuscript/CLAIMS.md`.

Обе таблицы — человеческие витрины и одновременно машинный контракт: строка
журнала и строка карты обновляются в том же шаге, что `registry.json`, отчёт или
статья (AGENTS.md §3a, §6a).

## Что здесь лежит

| Файл | Кто пишет | Смысл |
| --- | --- | --- |
| `registry.json` | человек/агент, вручную | Декларация экспериментов: статус, план, отчёт, артефакты, следующий шаг, научный цикл и очереди гипотез. |
| `state.json` | `scripts/lab.py state` | Сгенерированный снимок: фаза, активные прогоны, блокеры, диск. Не редактировать вручную. |
| `checkpoints.json` | `scripts/lab.py checkpoints` | Индекс весов: путь, размер, arm/seed/step, требования E02b, статус хеша. |
| `runs/<run_id>.json` | `scripts/lab.py run` / `journal-import` | Неизменяемый манифест прогона. Один прогон = один файл. |
| `logs/` | `scripts/lab.py logs-archive` | Тонкий архив завершённых per-run JSONL + `index.json`; TensorBoard и stdout не входят. |
| `experiments/E02b_morphospace.json` | человек, после закрытия | Машиночитаемый дескриптор E02b: `status`, `outcome`, `results`. Протокол и отчёт остаются в `reports/`. |
| `retention.json` | человек/агент | Удалённые веса: путь, размер, mtime, причина, канонический набор, который остался. |
| `schemas/` | человек | JSON Schema для registry/state/run/checkpoints/journal. |
| `locks/` | `scripts/lab.py claim` | Runtime-замки; в git не попадают. |

## Источник истины

Порядок старшинства:

1. **Сырые per-run артефакты и канонический журнал** — факт запуска.
2. **`runs/<run_id>.json`** — паспорт прогона: команда, сид, окружение, вход/выход.
3. **`registry.json`** — что мы считаем экспериментом и что дальше.
4. **`reports/` и `articles/`** — интерпретация; они не переписывают факты.

Агрегаты вроде `wp4_ablations.json` и `results.json` — представления. Если агрегат
расходится с первичным журналом или манифестом, прав первичный источник; агрегат
пересобирается, а не «подгоняется».

## Канонический журнал

Журнал прогонов — `morphogenesis/logs/journal.jsonl`. Это единственный файл в
`morphogenesis/logs/`, который отслеживается git: он append-only, маленький и
нужен для проверки пар start/finish на свежем клоне. Per-run JSONL, TensorBoard и
stdout-логи по-прежнему игнорируются.

Старый `morphogenesis/experiments/journal.jsonl` — legacy-журнал менеджера
экспериментов с текстовыми сообщениями. Он сохранён для аудита, но каноническим
не является.

Журнал не переписывается задним числом. Оборванный прогон остаётся видимой
дырой; его нельзя «закрыть» выдуманной finish-строкой.

## Прогоны и замки

Перед запуском агент занимает эксперимент:

```bash
python scripts/lab.py claim --experiment my_experiment --owner my-agent
```

Замок лежит в `lab/locks/<experiment>.lock` и содержит `run_id`, host, PID,
время старта и heartbeat. Правила простые:

- один writer на эксперимент;
- один training-прогон на GPU;
- чужие артефакты не перезаписываются;
- повторный запуск получает новый `run_id`, а не правит старый;
- stale-замок не удаляется молча: сначала проверяется, что процесс действительно
  мёртв; для этого есть `--steal-stale`.

Обёртка `run` сама берёт замок, пишет манифест, запускает команду из
`morphogenesis/`, складывает stdout в `morphogenesis/logs/<run_id>.log` и
закрывает манифест.

## Чекпоинты

Веса не коммитятся. `checkpoints.json` индексирует их для агентов:

- `family` — каталог, например `WP4_R-9_s2000_seed303`;
- `kind` — `best`, `final`, `iter_1000`;
- `canonical_for` — для какого эксперимента файл выбран;
- `sha256` — заполняется отдельно, после тяжёлых прогонов;
- `requirements` — что именно нужно E02b и чего не хватает.

Канонический файл для переписи — `nca_final.pt`, как в
`wp4_reach_probe.py`. `nca_best.pt` не подменяет `final` и по умолчанию не
хранится, если `final` уже есть: аудит держится на метриках, журнале и
манифесте, а не на второй копии весов.

## Логи и диск

На GitHub едут **маленькие текстовые следы**: канонический журнал, манифесты
прогонов, `lab/logs/*.jsonl` (1–2 МБ), `retention.json` и индекс чекпоинтов.
Веса, TensorBoard, stdout обёртки и кадры не коммитятся. Поэтому «логи на
GitHub» не означают «залить всё, что пишет обучение».

Порядок такой:

1. прогон закончился и есть пара start/finish;
2. `journal-import` закрывает манифест;
3. `logs-archive` копирует завершённый JSONL и пишет `lab/logs/index.json`;
4. `state` пересобирает снимок;
5. коммитятся только JSON/Markdown.

**Локально живут только канонические `nca_final.pt`** из требований
`checkpoints.json` плюс явно объявленный положительный контроль. `nca_iter_*`
удаляются после успешного finish; `nca_best.pt` — при наличии `final` или
готового следа в git; `nca_final.pt` закрытого/замещённого плеча — после
фиксации метрик, логов и манифеста. Каждое удаление пишется в
`retention.json` (путь, размер, mtime, причина), `freed_bytes` суммируется.
Удаление канонического `final` или последнего положительного контроля —
отдельное решение владельца.

При `< 10 ГБ` свободного места тяжёлый прогон не запускается: сначала архив
логов и чистка неканонических весов. Канон E02b — 12 файлов, а не все
когда-либо сохранённые снапшоты.

Рабочая политика памяти и диска — [`DISK.md`](DISK.md): что едет в GitHub, что
остаётся локально, что уезжает в Kaggle/HF, пороги и порядок уборки после
каждого прогона. Полные веса (6 ГБ) в GitHub не отправляются; для внешнего
хранения — Kaggle Dataset/HF, для воспроизведения — lite-пакет.

## Обновление

```bash
python scripts/lab.py checkpoints          # пересканировать веса
python scripts/lab.py journal-import       # обновить runs/ из журнала
python scripts/lab.py logs-archive         # архив завершённых JSONL для GitHub
python scripts/lab.py state                # пересобрать state.json
python scripts/lab.py validate             # проверить контракт
```

После изменения `registry.json` или завершения прогона нужно пересобрать
`state.json` и закоммитить маленькие JSON/Markdown. Веса, кадры и большие логи
не коммитятся.
