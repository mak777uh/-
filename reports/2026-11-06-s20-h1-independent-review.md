# S20 / H1 — независимая рецензия статьи 031: что подтвердилось, что нет

**Что это.** Отдельный агент-рефери (не автор) пересчитал числа статьи 031 из сырых JSON своими руками, не
пользуясь авторским скриптом проверки. Его вердикт: **держится с оговоркой**. Ниже — проверка его находок
и что из них следует.

## Находки рефери, которые ПОДТВЕРДИЛИСЬ

### 1. Покрытие R1 в S16 завышено (критично)
В `s16_e1b_full.json` **6 из 18 прогонов не проходят R1** — весь режим `drain_slow`
(`patch_inflow_rich = 0.5`): финальные живые 0, 0, 0, 0, 0, 2. Их окна обрезаны (1–6 из 6), у жадного плеча
окна 2–6 просто отсутствуют. В статье §9 сказано «R1 проверяется в каждом прогоне» — это **неверно**, и моя
собственная рецензия утверждала то же самое («R1 holds in all 9 S16 runs»), что тоже неверно.
**Проверено мной:** `R1 false: 6` из 18.

### 2. S18 «≤ 0.02» скрывает разброс по сидам (критично)
Разница hi−lo в плече `diverse` по сидам и окнам:
```
seed 1: +0.0033 +0.0113 +0.0118 +0.0263 +0.0153 -0.0160
seed 2: -0.0057 -0.0115 -0.0111 +0.0173 +0.0760 +0.1653
seed 3: -0.0061 +0.0022 +0.0195 +0.0214 -0.0348 -0.0919
```
Среднее ≤ 0.02 действительно, но **максимум по модулю 0.165**, и знаки разные. В плече `monopoly` максимум
0.0051. То есть снятие монополии **увеличило** разброс признака примерно в 19 раз, а статья называет это
«≤ 0.02». Формулировка «нуль» неверна: правильная — **«недостаточно мощности при n=3»**.

### 3. Монотонность S13 — эффект ПЕРВОГО окна, и к концу она разворачивается (самое слабое место)
```
low_density : 0.2214 0.1471 0.0654 -0.0008 -0.0191 0.0197
base        : 0.1178 0.0678 0.0396  0.0217  0.0446 0.0352
high_density: 0.0568 0.0374 0.0773  0.0466  0.0144 0.0204
```
Первое окно упорядочено чётко (0.221 / 0.118 / 0.057). Последнее — **нет**: 0.0197 / 0.0352 / 0.0204, то есть
у самой разреженной популяции остаток **наименьший**. Статья говорит «при низкой плотности места хватает всем —
и там разрыв максимален»: это верно только для начала.

### 4. «Четыре теста» — на самом деле два прогона
`s6_c3_double_baseline.json` и `s7_c3b_baseline_ABC.json` содержат **бит-в-бит одинаковые** плечи `control` и
`double` (проверено: `True`). То есть S6 и S7 — один и тот же прогон, к которому добавлено третье плечо.
Аналогично `s18.monopoly` совпадает с `s10.heritable`, а `s16.full` — с `s14.base`.

### 5. Пересадка в S10 не работала (нашёл я, рефери указал направление)
Проверка напрямую: обмен признаками между верхними и нижними 10 % клеток **уничтожает вариацию**
(std 0.0691 → 0.0000), потому что присваивает всем верхним одно значение, а всем нижним другое. После этого
`run.step()` восстанавливает признак при рождениях, и плечо `transplant` идёт как `heritable`. Это ровно тот
класс дефекта («манипуляция не доходит до динамики»), за который статья отзывает S6 v1 — но применённый к
тесту, который она оставляет.

## Что из этого следует

Все четыре пункта — не арифметические ошибки (числа сходятся), а **ошибки вывода**: статья заявляет больше,
чем данные поддерживают. Правки, которые нужно внести:

1. §9: «R1 проверяется в каждом прогоне» → «R1 пройден в 12 из 18 прогонов S16; 6 прогонов `drain_slow`
   вымерли и исключены».
2. §4.2: «≤ 0.02» → «среднее по сидам ≤ 0.02, но по окнам |hi−lo| достигает 0.165 при n=3 — это недостаток
   мощности, а не нуль»; добавить, что S18 `monopoly` = S10 `heritable`, то есть тесты частично дублируются.
3. §4.1: указать, что корреляция −0.57 считается по занятости **контрольного** плеча и падает до −0.38 на
   окнах 3–6; что монотонность S13 — эффект первого окна и к концу разворачивается.
4. Объявить пересадку S10 **невалидной**, а не «нулевой».

## Куда дальше

Статья после этих правок станет слабее по формулировкам, но честнее. Главный вывод («жадность переносится и её
выигрыш падает по мере заполнения зоны») остаётся, но опираться он должен на корреляцию с заполнением и на
