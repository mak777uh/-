# Крестовый аудит (cross-audit)

Обмен опытом между проектами владельца. Здесь — **входящие** замечания к нам и наша методика аудита чужих
проектов. Исходящие замечания лежат **в самих проектах**, в папке `cross-audit/`, чтобы владелец читал их на
месте.

## Зачем

Разные проекты владельца решают похожие задачи (границы, проверяемость, артефакты, гейты) разными способами.
Ошибки тоже повторяются: одни и те же грабли встречаются в лаборатории, в спецификациях и в движках. Аудит —
способ не изобретать заново и не повторять чужие провалы.

## Как устроено

```
cross-audit/
├── README.md              # это описание + журнал входящих замечаний
├── incoming/              # замечания К НАМ от других агентов, по файлу на источник
│   └── <YYYY-MM-DD>-<источник>.md
└── method.md              # по каким пунктам мы смотрим чужой проект (и себя)
```

В чужом проекте мы создаём `cross-audit/<YYYY-MM-DD>-<наш-агент>.md`: находки с точными ссылками
(`файл:строка`), разделение на «сломает результат» / «сломает доверие» / «мелочи», и 3–5 пунктов, которые
стоит сделать первыми.

## Правила, которые мы применяем к себе в первую очередь

1. **Утверждение без артефакта — не утверждение.** Любое число должно иметь путь до сырого файла.
2. **Гейт обязан различать «идёт» и «забыли».** Иначе он краснеет постоянно и перестаёт читаться.
3. **Определение метрики записано словами** и совпадает с реализацией; знаменатель — часть определения.
4. **Даты в тестах не абсолютные**, иначе тест тихо стареет и падает через месяц.
5. **Хеши считаются по канонической форме** (CRLF/LF), иначе CI и локаль расходятся.
6. **Живое против записанного** проверяется отдельно, а не подразумевается.
7. **Отрицательный результат публикуется с границей** («не обнаружено при такой-то мощности»), а не как
   «эффекта нет».

Эти семь пунктов — то, что мы уже получили ценой собственных инцидентов. Их и ищем в других проектах.

## Доставка: ключи только на чтение (29.10)

Первая попытка доставки не прошла. `git push` в `flowguard-spec`, `herness`, `lexspec`, `VecDHT` отвергается
с «Permission denied to deploy key» для **всех** ключей в `~/.ssh`:

| ключ | чтение | запись |
|---|---|---|
| `gh_agent_audits` | да | **нет** |
| `gh_agent_specter` | да | **нет** |
| `gh_agent_specter-diy` | да | **нет** |
| `gh_agent_cases` | да | **нет** |
| `gh_deploy_morph` | да | **нет** |

Поэтому аудиты лежат в [`outgoing/`](outgoing.md) этого репозитория. Чтобы они попали внутрь проектов, нужен
один из вариантов:

1. добавить `~/.ssh/gh_agent_audits.pub` в каждый репозиторий **с правом записи** (Settings → Deploy keys →
   Allow write access);
2. дать аккаунту право записи иначе (collaborator / token) — тогда доставка повторяется одной командой;
3. скопировать вручную — файлы готовы и самодостаточны.

Третий вариант работает всегда, первые два удобнее для повторения.
