Репозиторий — самый крупный в семействе (1628 файлов кода, 1453 файла лаборатории, 185 отчётов), и CI у него
не декоративный: **32 шага** в `ci.yml`, ещё 8 и 9 в `analysis.yml` и `nightly.yml`, матрица по двум ОС,
`paths-ignore` для машинного следа прогонов с объяснением, `fail-fast: false`. Я искал не «где мало проверок»,
а «где проверка слабее своего описания».

Находки разделены по их конвенции: **сломает результат** / **сломает доверие** / **мелочи**.

## F-1 (HIGH) — сломает доверие — `--strict` применяется в одном месте из семи: строгий режим возвращает 0, печатая предупреждения

**Воспроизведение.**

```
$ python scripts/lab.py validate --ci > /dev/null 2>&1; echo $?
0
$ python scripts/lab.py validate --ci --strict > /dev/null 2>&1; echo $?
0
$ python scripts/lab.py validate --ci --strict 2>&1 | tail -3
  - lit-board.B-077: принято 4 дн назад (> 3) — пора либо закрыть, либо отложить с условием
lab: есть предупреждения.
```

**Почему так.** В `scripts/lab.py` предупреждения добавляются в семи местах:

```
$ grep -n "warnings.append(\|(errors if strict else warnings)" scripts/lab.py
1286:  warnings.append(f"нет файла очереди: {rel(target)} — протокол claim не ведётся")
1317:  warnings.append(
1743:  warnings.append("lab/cycle.json: нет type (research|review) — выход prepare не проверяется")
1778:  warnings.append("lab/cycle.json: не указан owner")
1787:  warnings.append("lab/cycle.json: git недоступен — выход prepare не проверен")
1918:  warnings.append(f"{exp_id}.artifact_root пока нет: {root}")
1966:  warnings.append(f"checkpoint отсутствует: {path_value}")
1971:  (errors if strict else warnings).append(message)
```

Только **одна** из семи строк (1971) уважает `strict`. Остальные шесть добавляют предупреждение напрямую, и
`print_validation` возвращает `1 if errors else 0` — то есть при `--strict` и непустом списке предупреждений
код возврата **0**.

**Следствие.** Флаг, который в `--help` описан как «считать предупреждения ошибками», работает для одного
класса предупреждений из семи. Любой, кто поставит `--strict` в CI, чтобы гейт стал строгим, получит гейт,
который молча пропускает 6/7 предупреждений. Это ровно тот случай, ради которого в семействе придумано
правило «гейт без падающего случая — декорация»: здесь гейт **есть**, а падающего случая у него нет.

**Починка, минимальная.** Один хелпер и семь замен:

```python
def warn(msg: str, strict: bool, errors: list, warnings: list) -> None:
    (errors if strict else warnings).append(msg)
```

Плюс шаг в CI, который **доказывает**, что строгий режим падает: запустить `validate --ci --strict` на дереве,
где предупреждение заведомо есть (сейчас такое состояние — lit-board, 10 записей), и требовать exit 1.
Сегодня это самый дешёвый способ поймать регрессию: состояние уже содержит предупреждения.

## F-2 (MEDIUM) — сломает доверие — 32 шага в `ci.yml`, ни одного негативного контроля

**Воспроизведение.**

```
$ grep -c "name:" .github/workflows/ci.yml
$ grep -n "selftest\|negative\|mutation\|--inject" .github/workflows/*.yml || echo "нет ни одного"
нет ни одного
```

Проверки настоящие (`scripts/check_reviews.py`, `queue_runner.py --audit`, `check_readme_fresh.py`,
`metrics_registry.py --check`, `verify_e02c_numbers.py`, схема карточек прогонов). Но **ни одна из них не
доказана падающей**: нет шага, который подсовывает нарушение и требует exit 1.

**Следствие.** Если `check_readme_fresh.py` начнёт возвращать 0 на любом входе (изменился путь, проглотилось
исключение), CI останется зелёным, а витрина начнёт отставать от результатов молча. Для лаборатории, где
«витрина не отстаёт» — это заявление, а не пожелание, такая регрессия невидима.

**Починка.** Один шаг `negative-controls`, по образцу `flowguard-spec/lab/selftest-guards.sh`: для каждого из
проверяющих скриптов — фикстура-нарушение в `tmp`, ожидание exit 1, падение шага, если проверка вернула 0.
Начать можно с двух самых важных: `check_readme_fresh.py` и `queue_runner.py --audit`.

## F-3 (LOW) — мелочь — `paths-ignore` исключает `lab/state.json`, то есть состояние очереди не проверяется никогда

```
$ grep -A6 "paths-ignore" .github/workflows/ci.yml
    paths-ignore:
      - "lab/runs/**"
      - "lab/state.json"
      - "lab/logs/**"
      - "morphogenesis/logs/journal.jsonl"
      - "reports/figures/**"
```

Обоснование в комментарии честное: «сотни пушей в сутки и письма о падениях». Но `lab/state.json` — это
**состояние очереди**, а `queue_runner.py --audit` проверяет, что «статусы очереди совпадают с реальностью».
Коммит, который меняет только `state.json`, не запускает ни одного шага — включая ту проверку, которая как раз
про состояние.

**Починка.** Не исключать `lab/state.json` из `paths-ignore`, а исключить только `lab/runs/**` и логи; либо
добавить отдельную дешёвую работу `state-only`, которая гоняет один `queue_runner.py --audit` (секунды, без
установки зависимостей).

## Что я проверил и **не** нашёл проблем

- `ci.yml` не «зелёный по умолчанию»: `set +e` + явная проверка `code -ne 0` + `::error title=lab-contract`
  — правильный паттерн, и он есть в первом же шаге;
- матрица по двум ОС с `fail-fast: false` — прогон не скрывает вторую платформу;
- `permissions: contents: read` и `concurrency` с `cancel-in-progress` — минимальные права и без гонок;
- `analysis.yml` (8 шагов) и `nightly.yml` (9 шагов) — разделение тяжёлого и быстрого сделано, ночные
  прогоны не в критическом пути;
- контракт лаборатории действительно считает и печатает `counts` (31 эксперимент, 1315 прогонов, 2561 строка
  журнала) — числа берутся из дерева, а не из головы;
- `scripts/test_lib_tools.py` существует — то есть у библиотечных инструментов есть тест, пусть и не в CI.

## Что я не проверял

- 1628 файлов `morphogenesis/` — предметом был CI, а не научный код;
- `lab/runs/**` (1315 прогонов) и `reports/` (185 файлов) — не сверял числа отчётов с артефактами;
- `formal/` (7 файлов) — формальные модели не запускал;
- воспроизводимость E02b/E02c на чужой машине — для этого нужны веса, которых у меня нет.
