## 2. Что считается истиной

Приоритет источников:

1. сырые per-run артефакты и канонический журнал
   `morphogenesis/logs/journal.jsonl`;
2. `lab/runs/<run_id>.json` — команда, сид, окружение, входы и выходы;
3. `lab/registry.json` — что мы считаем экспериментом;
4. `reports/` и `articles/` — интерпретация.

**Слои артефактов (контракт v1.1).** Манифест `lab/runs/<run_id>.json` — факт о
запуске (команда, коммит, окружение, статус); научная карточка
`lab/science/<run_id>.json` — числа, **взятые из артефактов** (класс переписи,
метрики, пре-регистрация); `lab/runs.index.json` — представление для внешнего
мира (депозит, заявки, рецензент), собирается скриптом. При расхождении
приоритет: артефакт → карточка → индекс. Карточка не может противоречить
артефактам, индекс руками не правится. Подробности — §6b.

Агрегаты (`wp4_ablations.json`, `results.json`, таблицы в отчётах) —
представления. При расхождении пересобирай агрегат из первичных данных, а не
подгоняй первичные данные под красивую сводку.

Журнал append-only. Оборванный прогон остаётся видимой дырой. **Запрещено**
дописывать finish-строку задним числом, переписывать строки или «закрывать»
прогон, которого не было.

## 3a. Научный цикл: источники → гипотеза → проверка → статья → README → рукопись

Работа лаборатории — не набор разовых прогонов, а замкнутый цикл из восьми стадий.
Стадии идут по кругу, и переход к следующей обязателен:

1. **Работа с источниками в публикациях.** Что уже сказано в литературе по нашему
   вопросу, какие методы и какие оговорки. След — в [`library/`](library/README.md):
   конспект с DOI, свои заметки, короткие атрибутированные цитаты. Полные тексты
   чужих статей в репозиторий не копируются.
   **Любое обсуждение литературы — в библиотеку.** Если работа всплыла в разговоре
   (с владельцем, с внешним собеседником, в препринте), она попадает списком
   библиотекарю с форматом записи и блоком «Код и данные», а не остаётся в
   переписке. Утверждение из литературы либо имеет запись в `library/`, либо
   помечено как непроверенное.
   **Перед каждой новой волной:** `python scripts/library_digest.py` показывает,
   какие пункты библиотеки ещё не использованы. Взять 2–3 из них и ответить: что
   они меняют в формулировке гипотезы или вывода. Гипотеза, выросшая из источника,
   ссылается на него в `origin`/`test`; если литературу не проверяли — это
   пишется явно, а не замалчивается. «Прочитал и не повлияло» — тоже результат,
   его фиксируют строкой, чтобы не читать то же самое через неделю.
2. **Просмотр наших данных и статей.** Что уже измерено у нас: сырые артефакты,
   отчёты, версии статей. Новая гипотеза обязана опираться на наши же данные,
   а не на память и не на чужую статью.
3a. **Сверка с литературой как сужение.** Перед формулировкой гипотезы проверяем,
   не проверено ли уже: таблица «вопрос → что известно → что не делаем → что проверяем
   у себя → ожидание» в `docs/prior-art-*.md`. Известный результат берём как
   ограничение и не тратим на него прогоны.
3b. **Сверка с доской литературы.** Перед формулировкой гипотезы открыть замечания,
   адресованные этой цели (`lab/lit-board.json`, `python scripts/lit_board.py --for <id>`):
   это утверждения вида «это уже известно», «здесь нужен базлайн», «в науке это
   называется иначе», «вывод противоречит источнику». Каждое замечание получает
   решение ведущего: `accepted` (с указанием, что именно меняем), `declined` (с
   причиной) или `deferred` (линия приостановлена — вернуть при возобновлении).
   Библиотекарь замечания только заводит и никогда не закрывает.
3. **Наша проверяемая гипотеза.** Формулировка, которую можно опровергнуть: что
   измеряем, какой артефакт будет свидетельством, что считается опровержением.
   Фиксируется **до** запуска (pre-registration, `reports/`).
4. **Проверка.** Прогон, сырой артефакт, манифест `lab/runs/<run_id>.json`.
   Отрицательный результат — такой же результат.
5. **Отчёт и статья.** Отчёт в `reports/` — карточка эксперимента; текст в
   `articles/` — связный рассказ, который можно прочитать без репозитория.
6. **Строка в README.** Журнал экспериментов в [`README.md`](README.md): id,
   статус, вердикт одним предложением, ссылки на отчёт/статью/артефакт. Детали
   в README не переносятся — только вердикт и ссылки.
7. **Кусочек рукописи.** Результат, который идёт в публикацию, дописывается в
   [`manuscript/paper.md`](manuscript/paper.md) (абзац или подраздел), с записью
   в [`manuscript/CHANGELOG.md`](manuscript/CHANGELOG.md) и строкой в карте
   [`manuscript/README.md`](manuscript/README.md). Утверждение сверяется с
   [`manuscript/CLAIMS.md`](manuscript/CLAIMS.md).
8. **Работа с источниками → новая гипотеза.** Следующий виток: новые источники,
   новая гипотеза, снова проверка.

**Правило, обязательное на любой стадии.** Как только получен хороший научный
результат — положительный, отрицательный или промежуточный, — агент обязан:

- написать или обновить **статью**, а не только отчёт;
- обновить **строку журнала в README** (id, статус, вердикт, ссылки);
- добавить **кусочек в рукопись**: фрагмент `paper.md`, запись в `CHANGELOG.md`,
  строку карты в `manuscript/README.md`;
- явно указать **следующие гипотезы для проверки**: что именно проверять дальше,
  каким экспериментом и по какому критерию.

Статья без следующих гипотез считается незавершённой работой. Результат без
строки в README и без кусочка рукописи — тоже незакрытый результат: это не «когда
будет время», а часть определения результата (§6). Если следующий шаг требует
решения владельца, это фиксируется явно.

**Как это проверяется машинно.** Правило не остаётся на словах:

- `lab/registry.json` → `program.loop` — восемь стадий цикла;
- `lab/registry.json` → `program.next_hypotheses` — очередь гипотез лаборатории со
  статусом (`planned` / `running` / `confirmed` / `rejected` / `blocked`);
- у каждого закрытого эксперимента со статьёй — `next_hypotheses` с формулировкой,
  способом проверки и статусом;
- журнал README: каждый эксперимент из registry имеет строку, статус совпадает;
- карта рукописи: каждый закрытый эксперимент со статьёй имеет раздел и статус
  вклада;
- `python scripts/lab.py validate` падает, если цикл нарушен: нет стадий, пустая
  очередь гипотез, статья без следующих гипотез, гипотеза без критерия проверки,
  README расходится с registry, у закрытого результата нет места в рукописи.

Смену стадий цикла и статусов гипотез делает владелец; агент может предложить
правку отдельным коммитом и остановиться.
**Триггеры проверки литературы.** Когда в работе появляется одна из фраз — «нужен
параметр/механизм», «проигрывает/стало хуже», «собираемся перебирать», «не
проверяли» — это сигнал, что задача, скорее всего, уже сформулирована в науке.
Проверка идёт через очередь `lab/lit-queue.json` и `python scripts/lit_check.py`:
`--scan` находит такие места в текущих документах, `--list` показывает очередь,
`--done ID --result "..."` закрывает с итогом. Если из литературы следует
функциональная форма — реализуем её и тестируем против лучшего фиксированного
базлайна, а не против «случайно».

**Инсайт без действия не считается прочитанным.** Каждый вывод из литературы
регистрируется в [`lab/insights.json`](lab/insights.json) со **обязательным** полем
действия: `param` (новая опция в коде), `hypothesis` (гипотеза с критерием),
`task` (задача исполнителю), `experiment_change` (изменить уже запланированный
эксперимент — с полем, что именно меняется), `reprioritize` (переставить очередь или
задачи в более оптимальный порядок) или `none` (не применяем — обязательно причина).
Команды: `python scripts/insight.py --add ...`, `--apply ID`, `--decline ID --why ...`,
`--check` (падает, если инсайт старше 24 часов без действия).
Чтение в цикле: `library_digest.py` → `library_brief.py` → `insight.py` → задача.

**Убираем из плана — не стираем.** Идея, снятая с текущего плана (проверено
в литературе, не ко времени, дорого), кладётся в [`lab/pool.json`](lab/pool.json)
с условием возврата: при каком результате или вопросе к ней вернуться. Пул
смотрится перед новой фазой (`python scripts/pool.py`); если у пункта нет условия
возврата, он не нужен. Человеческий вид — [`docs/pool-deferred.md`](docs/pool-deferred.md).


## 3c. Проверка чувствительности до запуска

Правило, появившееся после двух нечувствительных серий подряд (kill-and-keep v1 и v2:
`pop_time` совпал до целого при ресурсе, различающемся в 5–6 раз).

**Ни один эксперимент «на разницу между плечами» не запускается, пока не посчитана
арифметика, которая эту разницу создаёт.** Для энергетических постановок:
`income = min(own, 4·b·own)`, трата `spent`, **точка безубыточности `own* = spent/(4·b)`**,
автономия `E/spent` шагов. Если всё поле в обоих плечах лежит **выше** порога (или всё
**ниже**), опыт нечувствителен **по конструкции**, независимо от числа сидов: клетки не
голодают ни там, ни там, и судьбу решает не то, что мы меняем. Числа `own*`, `spent`,
автономии и положение поля относительно порога пишутся в пре-регистрацию **до** критерия.

**Для отбора (E) аналог — расчёт мощности:** ожидаемый разброс признака (`sd`), фактор
эффекта (`1 ± eps·sd`), число линий, по которым считается ρ, и ожидаемая возможность
отбора `I = Var(w)/mean(w)²`, но **сравнивать её надо с нуль-моделью**: `I_obs > I_null(95 %)`, иначе ноль неотличим от демографического шума (Waples 2020; Waples & Reed 2023; инструмент — `library/tools/i_null.py`, поля `I_obs` / `I_null_95` / `I_ratio` обязаны быть в агрегате). Если ожидаемый |ρ| ниже порога манипуляционной проверки или
линий с данными меньше порога — серия невалидна по конструкции, и параметры меняются
**до** данных (как `mutation_trait_sigma` 0.01 → 0.05 и `eps` 0.1 → 2.0 в E).

**Знаменатель — часть определения величины.** Любая величина, считаемая по подмножеству прогонов
(«только валидные», «только с данными», «только завершившиеся»), обязана: (1) нести суффикс в имени
поля — `*_all` или `*_valid`; (2) иметь явный знаменатель в `metric` агрегата; (3) не называться так
же, как величина по всем прогонам. Основание: 25.10 агрегатор W2-bud считал `I > 0` только по валидным
прогонам (2 из 10), а критерий пре-регистрации требовал ≥7/10 по всем — агрегат «опроверг» выполненный
критерий, и это всплыло только при попытке автоматизировать сверку. Тогда же переименованы поля
`founding_matrix.by_n`: `n` = доза, и рядом `runs`/`valid_runs` — читалось как «n прогонов».
Проверка: `python scripts/verify_sections_numbers.py` (в CI) сверяет числа разделов рукописи с
агрегатами и падает при расхождении.

**Проверка пост-фактум:** в отчёте и в §-разделе линии пруда пишется строка «чувствительность:
`own*` = …, поле = …, вывод — чувствительно/нечувствительно». Нечувствительный результат
публикуется как «тест не дотянулся», а не как «эффекта нет».

## 4. Где и как запускать

Корень репозитория — для `scripts/lab.py`, тестов лабораторного контура,
отчётов и git. Экспериментальный код лежит в `morphogenesis/` и исторически
запускается с `cwd=morphogenesis/`, потому что пути в `config.py` относительны.
Импорт `morphogenesis.nca_core` из корня без подготовки падает на
`ModuleNotFoundError: No module named 'config'` — это известное ограничение, не
«фиксируй» его случайным изменением `sys.path`.

Длинные прогоны запускай только через обёртку:

```bash
# из корня репозитория
python scripts/lab.py run \
  --experiment WP4_R-9_s2000_seed404 \
  --experiment-id WP4 --arm R-9 --seed 404 --steps 2000 \
  --owner my-agent \
  --checkpoint-in morphogenesis/checkpoints/WP4_R-9_s2000_seed404/nca_best.pt \
  --output morphogenesis/checkpoints/WP4_R-9_s2000_seed404/nca_final.pt \
  -- python train.py --config ...
```

Обёртка:

- занимает замок `lab/locks/<experiment>.lock`;
- пишет `lab/runs/<run_id>.json` с git-коммитом, командой, окружением и CWD;
- запускает команду из `morphogenesis/`;
- пишет stdout в `morphogenesis/logs/<run_id>.log`;
- закрывает манифест и снимает замок.

Для интерактивного или внешнего запуска используй `claim` / `heartbeat` /
`release` вручную. Замок чужого агента не удаляется без проверки, что процесс
мёртв; для этого есть `--steal-stale`.

Правила конкурентности:

- один writer на эксперимент;
- один training-прогон на GPU;
- не перезаписывай чужие артефакты и не переиспользуй `run_id`;
- не трогай каталог активного прогона, пока не увидел finish в журнале;
- при падении оставляй `failed`/`aborted` и разбирайся, а не маскируй;
- **любой новый зонд или логгер обязан пройти якорь до серии.** Диагностика «только для чтения»
  может потреблять ГПСЧ и менять мир: 25.10 запись точки подсадки отдельным вызовом `_invader_spot()`
  сдвинула генератор, и якорь разошёлся (69217 против 66679). Ловится одним прогоном на якоре
  (≈90 с), а в данных — только после серии. Порядок: изменил `world/` или логгер → якорь бит-в-бит →
  серия.
- **не правь `morphogenesis/world/` и `run_pond.py`, пока идёт серия — даже
  аддитивно.** Каждый прогон — новый процесс, он подхватывает файл с диска в
  момент старта; правка посреди серии даёт «смешанное состояние кода»: часть
  прогонов падает, часть проходит на промежуточной версии. Инцидент 24.10 (серия
  D): 13 артефактов ушли в `quarantine/`, серия перезапущена целиком. Порядок:
  сначала финиш серии (или отдельная копия каталога), потом правка, потом
  контроль воспроизводимости на дозе/сиде-якоре до нового запуска.

**Если в репозитории работает больше одного агента**, запуску предшествует не
замок, а пункт очереди: `lab/queue.json` и `python scripts/lab.py item-claim`
(см. [`lab/README.md`](lab/README.md)). Claim берётся **до** пре-регистрации;
статус `running` означает занятый GPU-лейн и может быть только у одного пункта;
закрывает пункт тот, кто его вёл, второй агент только проверяет артефакты.
`python scripts/lab.py validate` падает, если в очереди два `running` или пункт
ссылается на несуществующую гипотезу.

**`--owner` — метка агента, а не человека.** У разных агентов разные метки
(например `lead`, `analyst`): защита от перехвата сравнивает владельца с
владельцем, поэтому две сессии с одинаковой меткой не различимы и могут забрать
чужой claim молча.

## 4a. Роли в контракте артефактов (v1.1)

Разделение нужно, чтобы научные числа не заполнял тот, кто отвечает за CI, и
наоборот.

- **Оператор (репозиторий/CI).** Схемы `lab/schema/`, валидатор, конвертер
  истории, сборка индекса, CI-гейты, теги и релизы внутри репозитория. Научные
  поля карточек не заполняет.
- **Учёный (исполнитель и ведущий на своих прогонах).** `class`, `metrics`,
  `preregistered`, `docs/protocol.md`, планирование матрицы экспериментов.
  Отвечает за то, что числа в карточке совпадают с артефактом.
- **Деньги (агент по грантам и внешней упаковке).** Заявки, депозит, внешняя
  коммуникация. В репозиторий не пишет: изменения просит через
  [`lab/notices.md`](lab/notices.md).
- **Владелец.** Научная рамка, критерии, новые тренировочные серии, любая
  публикация наружу.

## 4b. GitHub Actions — третья вычислительная машина

Кроме локальной GPU и CPU у лаборатории есть **бесплатный CPU GitHub Actions** (публичный
репозиторий → минуты не списываются). GPU там нет, поэтому CI — это **проверка
переносимости**, а не производство науки:

- канарейка мира (`scripts/ci_canary_pond.py`): короткий прогон пруда на чужой ОС, проверка
  детерминизма по сиду и согласованности счётчиков;
- пересчёт агрегатов, вердиктов и чисел рукописи из артефактов;
- `library_inbox --ci` (замечания библиотеки не гниют), контракт, тесты;
- ночной прогон `nightly.yml` (03:00 MSK).

**Напоминание, обязательное в каждом цикле:** раз в день проверить, есть ли импактная
CPU-задача для CI (правило выбора — [`docs/ci-resources.md`](docs/ci-resources.md) §«Как
выбирать импактную задачу на день»). Тяжёлые серии и обучение в CI не запускаются: нет GPU,
и это тратит время раннера без научной пользы.

## 5. Чекпоинты

- Канонический файл для E02b — `nca_final.pt`, как в `wp4_reach_probe.py`.
  `nca_best.pt` не подменяет `final` и по умолчанию не хранится, если `final` есть.
- Веса не коммитятся. Индекс — `lab/checkpoints.json`.
- Не удаляй и не перемещай чужие чекпоинты. Свои неканонические веса удаляются
  только по правилу §5a, с записью в `lab/retention.json`; канонический `final`
  и последний положительный контроль — только по решению владельца.
- `sha256` канонических файлов считается после закрытия активных прогонов:
  `python scripts/lab.py checkpoints --hash-canonical`.
- Отсутствующий чекпоинт нельзя заменить «похожим» (например, s400 вместо
  s2000) без явной поправки к протоколу.

## 5a. Логи и диск

GitHub — это **тонкая память**, а не хранилище весов. В git едут:

- канонический журнал `morphogenesis/logs/journal.jsonl`;
- манифесты `lab/runs/*.json`;
- `lab/logs/*.jsonl` + `lab/logs/index.json` (завершённые per-run логи, ~1 МБ);
- отчёты, статьи, JSON-агрегаты, фигуры, `lab/retention.json`.

Не едут: `.pt`, TensorBoard, stdout обёртки, `logs_*.txt`, кадры, кеши. Полные
локальные логи можно удалять только после `logs-archive` и только если они не
нужны активному разбору.

Порядок после finish:

```bash
python scripts/lab.py journal-import
python scripts/lab.py logs-archive
python scripts/lab.py state
```

**Правило локального хранения весов.** Локально живут только канонические
`nca_final.pt`, перечисленные в требованиях `lab/checkpoints.json` для активной
или следующей серии, плюс явно объявленный положительный контроль. Всё
остальное — расходник:

1. `nca_iter_*` удаляются после успешного finish и при наличии `final`;
2. `nca_best.pt` удаляется, если рядом есть `final` или если метрики плеча уже
   в git;
3. `nca_final.pt` закрытого/замещённого плеча удаляется после того, как его
   метрики, per-run JSONL и манифест зафиксированы в git.

Перед удалением в `lab/retention.json` пишутся путь, семейство, размер, mtime и
причина; `freed_bytes` суммируется. Веса в GitHub не отправляются — в репо
уезжает **след**, а не файл. Удаление канонического `final` или последнего
положительного контроля — отдельное решение владельца.

Перед запуском проверь `state.disk.free_gb`: при **< 10 ГБ** не стартуй тяжёлый
прогон, сначала архивируй логи и почисти неканонические веса. После каждого
закрытого прогона проверяй, что `lab/checkpoints.json` не раздулся: канон —
12 файлов E02b, а не все когда-либо сохранённые снапшоты.

## 6. Обязательный след эксперимента

Эксперимент считается завершённым, только если есть:

1. сырые артефакты в `morphogenesis/experiments/...`;
2. манифест `lab/runs/<run_id>.json` со статусом и окружением;
3. пара start/finish в каноническом журнале (или честный `failed`/`aborted`);
3a. **научная карточка** `lab/science/<run_id>.json` для каждого прогона, у
   которого была перепись: класс, метрики, ссылка на `census`/`summary`,
   `preregistered` (правила — §6b);
3b. **индекс пересобран**: `python scripts/build_runs_index.py`, и
   `lab/runs.index.json` не разошёлся с файлами (CI проверяет diff);
3c. если прогон был тренировкой без переписи, карточка не требуется, но манифест
   обязан быть закрыт (`status != running`) — «висящий» прогон не считается
   следом;
4. обновлённый `lab/registry.json`, если изменился статус или следующий шаг;
5. отчёт в `reports/` с числами и ссылками на артефакты; отрицательный
   результат публикуется наравне с положительным.
   **Исключение — линия пруда W1** (решение владельца 24.10): карточкой результата
   служит раздел `docs/world-design.md` §10<буква> вместе с агрегатом в
   `morphogenesis/experiments/E09_pond/*.json`; `reports/` для этой линии хранит
   **пре-регистрации** (`*-plan.md`). Причина: 20+ серий линии уже описаны так, и
   дублирующая карточка не добавляет трассировки — числа и артефакты те же.
   Проверка (внедряется): у закрытого пункта очереди линии пруда есть §10-раздел и
   агрегат, у агрегата — `aggregate_check` без ошибок;
6. статья обновлена и следующие гипотезы записаны — по правилу §3a это часть
   определения результата, а не отдельная задача;
7. строка журнала в [`README.md`](README.md): id, статус, вердикт, ссылки;
7a. **доска литературы:** в отчёте строка «доска: принято N, отклонено M,
   отложено K» с причинами — иначе замечания не проверяются и доска гниёт;
8. кусочек рукописи: фрагмент [`manuscript/paper.md`](manuscript/paper.md),
   запись в [`manuscript/CHANGELOG.md`](manuscript/CHANGELOG.md), строка карты
   в [`manuscript/README.md`](manuscript/README.md), при необходимости —
   утверждение в [`manuscript/CLAIMS.md`](manuscript/CLAIMS.md);
8a. `python scripts/claims_lint.py` — утверждение с новым числом обязано иметь тип основания
   (`доказательство` / `тест` / `статистика` / `наблюдение` / `суждение`), допущения и «что
   остаётся обосновать»; опровергнутый механизм — строкой в [`docs/eliminations.md`](docs/eliminations.md);
9. `python scripts/lab.py state && python scripts/lab.py validate`;
10. коммит и push без force.

Перед коммитом:

```bash
cd morphogenesis && python -m pytest -q tests && cd ..
python run_tests.py --quick        # то же плюс проверка рабочего каталога
python scripts/lab.py validate
```

## 6a. README и рукопись: правила ведения

README — витрина и карта, а не журнал. Журнал — `reports/`, машинное состояние —
`lab/`. Рукопись — `manuscript/`, единственное место будущей научной статьи.

### README

0. **Язык.** `README.md` — **английский** (витрина для грантов и внешних читателей); научный след
   (рукопись, отчёты, статьи, docs/) — русский. Метки статусов в журнале принимаются на обоих
   языках (`закрыто`/`closed`, `идёт`/`running`, `план`/`planned`, `заблокировано`/`blocked`,
   `не запускался`/`not run`), проверка — `lab.py validate`.
1. **Один экран.** Целевой объём 150–220 строк. Новый раздел добавляется только
   если его нельзя выразить строкой таблицы или ссылкой.
2. **Журнал экспериментов.** Одна строка на `experiment_id` из
   `lab/registry.json`: id, статус, период, вопрос, вердикт одним предложением,
   ссылки. Для активного эксперимента допускается абзац 2–4 предложения; для
   закрытого — только строка. Гипотезы, сиды и per-run числа в README не
   переносятся.
3. **Формат проверяется машинно.** Таблица лежит между маркерами
   `<!-- ledger:start -->` и `<!-- ledger:end -->`; первая ячейка — id (несколько
   id можно перечислить через запятую), вторая — статус: `закрыто`, `идёт`,
   `план`, `заблокировано`, `не запускался`. Дубли id и неизвестные id — ошибка.
4. **Числа.** Не более 3 «якорных» чисел на эксперимент, каждое обязано быть в
   отчёте или артефакте. Числа, которых нет в отчёте, в README не появляются.
5. **Синхронность.** Строка журнала и статус обновляются в том же коммите, что
   `registry.json`, отчёт или статья: старт, блокировка, закрытие, смена
   вердикта. Обновление README — пункт §6, а не отдельная задача.
6. **README не append-only.** Устаревшие строки и разделы переписываются или
   удаляются; история остаётся в git и `reports/`. Запрет «не переписывать
   задним числом» относится к отчётам и журналу, но не к README.
7. **Не дублировать.** Программа — `articles/001`, результаты — `reports/`,
   контракт — этот файл, спецификация — `docs/spec/`, источники — `library/`.
   В README — ссылка, а не пересказ.
8. **Структура.** При добавлении/удалении верхнеуровневого каталога или скрипта
   обновить дерево; глубина — 1–2 уровня, исчерпывающим оно быть не обязано.
9. **Дата.** В заголовке статуса — не дата, а одна строка `Обновлено: YYYY-MM-DD`
   (или ничего): дата в заголовке устаревает быстрее содержимого.

### Рукопись

10. **Один закрытый результат = один кусочек.** `paper.md` получает абзац или
    подраздел, `CHANGELOG.md` — запись (дата, эксперимент, раздел, что
    добавлено, источник), `README.md` рукописи — строку карты, `CLAIMS.md` —
    утверждение с доказательством. Отрицательный результат входит наравне.
11. **Рукопись не переписывает статьи.** `articles/` — текст об одном
    эксперименте, `manuscript/` — накопительная публикация. Числа в рукописи
    сверяются с отчётами; при расхождении прав отчёт.
12. **Версии.** `paper.md` начинается с версии `v0.x`; старые записи
    `CHANGELOG.md` не переписываются, уточнение — новой записью. Перед подачей
    рукопись замораживается отдельным тегом.
13. **Гейт публикации.** Подача возможна только после закрытия E02c и
    независимого воспроизведения, по решению владельца. Формулировки «жизнь»,
    «сознание», «интеллект» запрещены (§3); в рукописи — наблюдаемый класс
    поведения и его границы.

### Машинная проверка

`python scripts/lab.py validate` проверяет: маркеры и таблицу README, покрытие
всех `experiment_id`, совпадение статусов; маркеры и карту рукописи, покрытие
закрытых экспериментов со статьёй, допустимые статусы вклада. CI запускает ту же
проверку (`lab.py validate --ci`).

## 6b. Контракт артефакта v1.1: как заполнять научную карточку

Схемы: [`lab/schema/run.schema.json`](lab/schema/run.schema.json) (карточка) и
[`lab/schema/runs_index.schema.json`](lab/schema/runs_index.schema.json) (индекс).
Проверка: `python scripts/validate_runs.py` (CI запускает её до тестов).

1. **Источник чисел — только артефакты в git**: `summary_*.json` (класс,
   устойчивость), `morphogenesis/logs/journal.jsonl` (`best_loss`,
   `alive_fraction_final`, `wall_time_sec`), `lab/checkpoints.json` (sha256),
   манифест прогона. Нет данных — `null` и запись в `notes`, а не оценка.
2. **`regime` — точность, не железо**: `tf32` \| `fp32` \| `fp32_no_tf32_hw`
   (карта без TF32: Turing T4/V100) \| `cpu` \| `unknown`. Карта, драйвер, версии
   torch/CUDA — в `env`, а не в `regime`.
3. **`class`** — доминирующий класс переписи: `struct_1`, `struct_2`,
   `uniform_dark`, `uniform_bright`, `death`, `mixed` (порог 52/64 не взят ни
   одним классом), `n/a` (переписи не было), `unknown`. Нестандартное имя — в
   `class_extra` и отдельным решением расширить enum.
4. **`preregistered`**: `true` — только если в репозитории есть план с критерием,
   закоммиченный **до** старта прогона (в `notes` — хеш коммита); иначе
   `unknown`. Задним числом `true` не ставится.
5. **`weights_sha256`** — если файл весов существует, хеш обязателен и должен
   совпадать с `lab/checkpoints.json` или с файлом.
6. **Кто заполняет.** Научные поля — учёный (исполнитель или ведущий на своих
   прогонах). Оператор заполняет только `source: converted` через скрипт.
7. **Закрытая карточка не редактируется задним числом.** Уточнение — новой
   карточкой (новый прогон) или явным полем `notes`, но не правкой класса и
   метрик закрытого результата.
8. **Ссылки обязательны:** `summary`, `census`, `report` — чтобы из депозита была
   трассировка до артефакта и человеческого текста.
9. **Три координаты класса** (протокол [`docs/protocol.md`](docs/protocol.md)):
   режим, горизонт обучения и **длина роллаута** при переписи. Утверждение без
   любой из них не принимается. Для заявленного класса прикладывается кривая
   «класс от длины роллаута» (`scripts/census_curve.py`), потому что траекторный
   зонд показал: класс меняется по ходу обучения (1000 → `uniform_dark`, 2000 →
   `struct_2`, 3000 → `struct_1`, 4000 → `death`).
10. **Лизии оцениваются класс-независимо**: восстановление = вернулся ли любой
   устойчивый порядок, время оседания, IoU, доля живых; класс — справочная метка.
11. **Два базлайна**: `untrained_current_arch` и `random_init`
   (`morphogenesis/make_random_init.py`), второй — в масштабе обученных весов.

## 6c. Формальные гипотезы (Lean)

Третий инструмент рядом с CPU и GPU. Формальная гипотеза — теорема о наших
определениях или инвариантах; её проверка машинная.

1. **Идентификатор** `F-<область>-<номер>`; в шапке `.lean`-файла — формулировка,
   что опровергнет и какое место в питоне теорема защищает.
2. **Питоновский аналог** — тест на конкретных числах, либо явное объяснение,
   почему его нет.
3. **Проверка:** `python scripts/lean_check.py`; инвентарь `lab/formal.json`
   коммитится. Если Lean не установлен (CI), это пишется как `skipped`, а не
   «доказано».
4. **В отчёте:** id, что доказано, что осталось вне формализации, и какими данными
   теорема проверяется на практике.
5. **Не формализуем:** поведение обученной сети (плавающая точка), статистические
   утверждения, «жизнь/агентность/открытость» (нет определения). Подробности и
   честные замены — [`docs/formal-method.md`](docs/formal-method.md).
6. **Топология:** утверждение «правило сохраняет χ» ложно в общем случае; законная
   форма — `|Δχ| ≤ K` за шаг.

- Оставлять после себя замок, фоновый процесс или «временный» файл в
  отслеживаемом каталоге.
- Закрывать научный результат без статьи и без записанных следующих гипотез
  (§3a): «потом напишу» — не причина, `lab.py validate` это отслеживает.
- Публиковать наружу (Zenodo, Giveth/Gitcoin, arXiv, депозиты, заявки с
  артефактами) без явного «ок» владельца.
- Править научную карточку `lab/science/<run_id>.json` закрытого прогона задним
  числом: класс и метрики закрытого результата не переписываются (§6b).
- Класть в карточку числа, которых нет в артефактах, — в том числе
  «примерно», «по памяти», «из графика».
- Править `lab/runs.index.json` руками: он всегда пересобирается скриптом.
- Выдавать `make repro` в CI за воспроизведение на GPU: у раннеров нет GPU, и
  `repro/README.md` это фиксирует.

## 8. Git и коммуникация

- Один логический шаг — один коммит; сообщение объясняет «почему».
- Перед коммитом проверь `git status` и убедись, что не добавлены веса, логи,
  секреты и чужие незавершённые артефакты.
- Пуш — только обычный fast-forward. После пуша обнови `lab/state.json`, если
  он зависел от локального состояния.
- Если работа заблокирована чужой задачей, зафиксируй это в
  `lab/registry.json` (`blockers`) и в отчёте, а не обходи молча.
- Для человека итог формулируй так: что сделано, что найдено, что дальше, где
  лежат доказательства.
- **Теги.** `v1.x.y` ставится только при зелёном CI и после локального
  `make repro` (лог прикладывается к отчёту; в CI этот шаг не идёт). Тег не
  двигается задним числом: новая версия — новый тег. Публикация депозита по
  тегу — только по «ок» владельца.
- `_zenodo/`, `_hourly/grants/` и прочие внешние рабочие каталоги не коммитятся:
  в репозитории живёт след работы, а не черновики переписки.

## 9. Быстрые команды

```bash
# из корня
python scripts/lab.py status
python scripts/lab.py validate
python scripts/lab.py checkpoints
python scripts/lab.py journal-import
python scripts/lab.py state

# тесты (cwd=morphogenesis обязателен)
cd morphogenesis && python -m pytest -q tests

# контракт артефактов v1.1
python scripts/validate_runs.py          # карточки lab/science/ по схеме
python scripts/build_runs_index.py       # пересобрать lab/runs.index.json
python scripts/convert_runs.py           # история → карточки (только из артефактов)

# библиотека: что прочитано, что не использовано
python scripts/library_digest.py

# матрица утверждений и единый гейт
python scripts/claims_lint.py        # тип основания, допущения, ссылки на артефакты
make verify                          # всё сразу: контракт + claims + ссылки + Lean без sorry

# локальный CI
python run_tests.py --quick

# smoke-воспроизведение (только локально, нужен GPU)
make repro
```

Если команда не помещается в эти правила — остановись и спроси владельца.
