# Инструменты и софт для задач нашего типа: обзор и что брать

Запрос владельца: что народ применяет к таким задачам (ALife, клеточные автоматы, эволюция
правил, метрики открытости), что из этого полезно нам и **где кроме Lean**.

Проверка живости: GitHub API (`stargazers_count`, `pushed_at`, `archived`) на 2026-10-24;
версии PyPI — в тот же день; публикации — Crossref (DOI указаны). Звёзды — не качество, но
показывают, живой ли проект; «archived» — красный флаг.

## 1. Короткий вывод (что делать)

1. **Hypothesis** (property-based testing) — самая дешёвая и полезная вещь из всего списка:
   проверять инварианты пруда (энергия не отрицательна, клетка не умирает дважды, тип не
   теряется, счётчики согласованы) на случайных сценариях. Цена: 1 день.
2. **Z3** — точечные инварианты и «а есть ли вообще состояние, где X?» (SMT). Цена: 2 дня.
3. **nolds + antropy** — суррогаты и энтропии для метрик: закрывают наш тройной контроль
   (замёрзшее поле / белый шум / структура) без своего кода. Цена: полдня.
4. **Napari** — просмотр 3D/многоканальных состояний NCA и пруда; заменяет самописные GIF.
   Цена: 1 день.
5. **Snakemake или DVC** — только если серии станут больше, чем `lab.py` удобно тянет;
   сейчас у нас уже есть обёртка, дублировать не надо.
6. **TLA+** — только для протокола (замки/claim/очередь), не для физики пруда. Цена: неделя.
7. **Не брать**: Mesa/NetLogo как замену нашему миру (дорого, ничего не даёт), EvoJAX
   (archived), Golly (desktop, не для серий), QDax/pyribs — только если реально пойдём в QD.

## 6. Где ещё, кроме Lean: формальные методы по цене

Lean у нас используется для теорем об определениях/инвариантах (F-серия). Но большинство наших
рисков — не «доказать теорему», а «поймать баг в правилах и протоколе». Для этого есть более
дешёвые инструменты.

| Инструмент | Что проверяет | Цена входа | Приоритет для нас |
|---|---|---|---|
| [Hypothesis](https://github.com/HypothesisWorks/hypothesis) 6.170.9 | свойства кода на случайных входах: «энергия ≥ 0», «нет двойной смерти», «тип сохраняется» | 1 день | **1 — брать сейчас** |
| [Z3](https://github.com/Z3Prover/z3) 5.3.1.0 (PyPI) | SMT: «существует ли состояние, где инвариант нарушен»; проверка арифметики ресурсов | 2 дня | **2 — точечно** |
| [TLA+](https://github.com/tlaplus/tlaplus) / TLC | протокол: замки, claim, очередь, жизненный цикл прогона | 1 неделя | **3 — только протокол** |
| [Alloy](https://github.com/alloytools/org.alloytools.alloy) | реляционная модель: артефакты/карточки/индекс, поиск контрпримеров | 2–3 дня | **4 — если будет время** |
| [Dafny](https://github.com/dafny-lang/dafny) | верификация кода с контрактами | недели | **5 — не сейчас** |
| [deal](https://github.com/life4/deal) / [icontract](https://github.com/Parquery/icontract) | runtime-контракты в Python | часы | **1б — дёшево, как дополнение к Hypothesis** |
| CrossHair | символическое исполнение Python-функций | 1–2 дня | **4 — точечно** |
| Coq/Isabelle | большие доказательства | месяцы | **не надо** |

Почему такой порядок: Hypothesis ловит именно те баги, которые у нас уже были (наследование
типа, стартовый состав, двойной учёт смертей), и стоит день. Z3/TLA+ нужны там, где есть
протокол (замки, claim, очередь) — это наша `lab.py`-инфраструктура, а не физика. Lean
остаётся для теорем, которые нельзя проверить примерами.

## 8a. Дифференцируемый soft-pond (D-35): чем делать

Пул D-35: «обучать правило на семьях сред» требует дифференцируемого пруда, потому что цикл
рождений/смертей дискретен и градиента через него нет. Три варианта, по возрастанию цены:

| Вариант | Стек | Живость | Плюсы | Минусы |
|---|---|---|---|---|
| **A. PyTorch + soft-пороги** (рекомендую) | `torch` уже стоит (NCA на нём) | — | ноль новых зависимостей; sigmoid/straight-through; autograd; тот же GPU-путь | мягкие пороги дают смещение; нужна проверка «soft → hard» на тех же сидах |
| B. JAX + Equinox + Diffrax | [jax](https://github.com/jax-ml/jax) 36k★ (push сегодня), [equinox](https://github.com/patrick-kidger/equinox) 3k★, [diffrax](https://github.com/patrick-kidger/diffrax) 2.1k★ | все живы | jit/vmap, быстрее на свипах; diffrax для ODE-взгляда | второй стек; наши тесты/обёртки на torch |
| C. Gradient-free ES | [evosax](https://github.com/RobertTLange/evosax) 803★ | жив | не нужны мягкие пороги; можно на дискретном пруде | дороже по прогонам; шум |
| (для справки) | [torchdiffeq](https://github.com/rtqichen/torchdiffeq) 6.5k★, [jax-md](https://github.com/google/jax-md) 1.5k★ | живы | ODE/молекулярная динамика | нам не нужно |

**Рекомендация.** Начать с **A**: soft-версия в torch, где жёсткие пороги заменены сигмоидами с
температурой, и обязательный контроль «soft-модель на тех же сидах воспроизводит hard-результаты
при T→0». Только если скорость станет узким местом — переезд на B; ES (C) — если градиент
через мягкие пороги окажется нестабильным.

**Осторожно.** Дифференцируемость не делает задачу честной: мягкий порог — это другая модель.
Нужен тест «soft vs hard» на 3 сидах и явная оговорка в тексте, что обучали на релаксации.

## 9. Чего не делать

- **Не переезжать на Mesa/NetLogo/Agents.jl**: наш мир — собственный, а обёртки `lab.py`
  уже дают манифесты и журнал; переезд даст месяц работы и ноль новых результатов.
- **Не ставить MLflow/W&B поверх `lab/runs`**: дублирование трекинга, два источника правды.
- **Не тащить Coq/Isabelle**: у нас нет теорем такого масштаба; Lean-серия уже покрывает
  нужное.
- **Не брать EvoJAX** (archived) и **Sacred** (замедляется).
- **Не начинать с TLA+**: сначала Hypothesis — она ловит те же классы ошибок дешевле.
