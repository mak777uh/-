# Публикационная практика NCA/Alife: 12 полей

Схема полей и три заполненные работы. `?` — **не проверено**, а не «нет». Цитаты
короткие и атрибутированные; источник заполнения указан в колонке «Сверено».

## Схема

| # | Поле | Что значит |
| --- | --- | --- |
| 1 | Источник | DOI/arXiv + год; издание |
| 2 | Субстрат | NCA/Lenia/иное, фреймворк |
| 3 | Что утверждается | одна фраза: главное утверждение работы |
| 4 | Сиды/повторы | сколько прогонов, сообщён ли разброс |
| 5 | Горизонт обучения | сколько шагов/итераций; назван ли в тексте |
| 6 | Оцениваемый чекпоинт | финальный, лучший, последний из нескольких |
| 7 | Режим точности и железо | TF32/FP32/AMP, GPU; обсуждается ли |
| 8 | Untrained-базлайн | есть ли контроль «необученная архитектура» |
| 9 | Random-init-базлайн | есть ли контроль «случайная инициализация в масштабе обученных весов» |
| 10 | Устойчивость класса | есть ли перепись/повтор класса как процедура |
| 11 | Код | открыт ли код, где |
| 12 | Данные/веса | опубликованы ли чекпоинты, сырые прогоны, датасеты |

## Что искать в первую очередь (из notices)

1. Работа, где «структура из шума» заявлена **с** untrained-базлайном — контрпример к
   нашей претензии к полю.
2. Работа, где выученный класс **переносится** между режимами точности (AMP, мультидевайс,
   bf16) — контрпример к H-REPRO-1/H-REPRO-8.
3. Любая работа, где класс/режим явно задан как функция горизонта, — опора для «окна»
   (уже добавлены R8 Nakkiran и R9 Power в `../hypotheses/reproducibility.md`).

## Как заполнять

1. Читать полный текст (или авторский препринт). Не заполнять по аннотации.
2. Цитату — только если она прямо подтверждает поле; ≤ 20 слов, с кавычками.
3. `?` честнее, чем догадка. В колонке «Сверено» — дата и кто проверял.
4. Ошибку исправлять с пометкой «уточнено ДД.ММ.ГГГГ».

## Куда публиковать отрицательные результаты (Q7, 2026-10-24)

Проверка: есть ли у ALife отдельная площадка для отрицательных результатов. **Отдельного
трека/журнала именно для ALife не нашлось**; работают четыре формата:

1. **Полная статья с отрицательной рамкой** — ALIFE conference / *Artificial Life* journal:
   отрицательный результат проходит как обычная статья, если есть механика, карта условий и
   воспроизводимость (наш случай §4b/§4c/§4e).
2. **ReScience C** — воспроизведения и отрицательные результаты; формат: код + окружение +
   что не воспроизвелось ([10.1007/978-3-030-23987-9_14](https://doi.org/10.1007/978-3-030-23987-9_14)).
3. **Registered Reports** — пре-регистрация до анализа, где площадка их принимает
   ([10.1027/1864-9335/a000192](https://doi.org/10.1027/1864-9335/a000192), Nosek &
   Lakens 2014, *Social Psychology*; уточнено 24.10.2026 — раньше стоял препринт
   10.31234/osf.io/mgxyg).
4. **Workshops** — самый дешёвый способ показать отрицательный результат до полной статьи.

Почему это стоит делать, а не прятать: положительный сдвиг публикационного отбора хорошо
задокументирован, и «непубликуемые» отрицательные результаты искажают поле
([10.11613/bm.2017.030201](https://doi.org/10.11613/bm.2017.030201), Mlinarić et al. 2017,
*Biochemia Medica*). Обратная асимметрия тоже бывает — в некоторых областях отбор
благоприятствует нулевым/отрицательным результатам
([10.1136/bmjebm-2023-112292](https://doi.org/10.1136/bmjebm-2023-112292), Ioannidis 2023,
*BMJ Evidence-Based Medicine*); это аргумент формулировать результат нейтрально, а не
«драматизировать».

**Вывод для пути C.** Наш формат: полная статья с картой условий + возможный ReScience-реплей
ключевого отрицательного результата (B2/L2). Отдельного ALife-трека ждать не нужно.

## ReScience C: что требуется по факту (прочитано 24.10.2026)

Площадка: [rescience.github.io](https://rescience.github.io/), ISSN 2430-3658, platinum open access,
CC BY. Описание инициативы — [Rougier et al., 2017, PeerJ CS 3:e142](https://doi.org/10.7717/peerj-cs.142).

**Требования к подаче** ([write](https://rescience.github.io/write/)):
1. код — публичный репозиторий; данные — публичный архив (Zenodo, DOI после принятия);
2. статья по LaTeX-шаблону (или собственный) + метаданные по шаблону;
3. подача — issue в `rescience/submissions`; ревью публичное, **двое рецензентов запускают код**;
4. критерии: строгая методология, оригинальный код, существенные свидетельства воспроизведения
   **или** объяснение, почему результат не воспроизводится;
5. нельзя воспроизводить свою работу или работу близких коллег;
6. при провале — документировать и **попытаться связаться с авторами** оригинала.

**Что это значит для наших отрицательных результатов.** ReScience C — про воспроизведение
**чужого**, а не про отчёт о своём. Прямой путь туда есть только через [Re]-формулировку:
взять опубликованное плечо (например, выгоду строительства или порог выгоды) и показать, что в
наших условиях оно не держится. Наши собственные отрицательные результаты — ALIFE/ArtLife,
воркшопы (см. раздел выше).

## Пре-регистрация в ALife (Q18, 2026-10-24)

Отдельного стандарта пре-регистрации для ALife нет. Работает общая дисциплина:

**[The preregistration revolution](https://doi.org/10.1073/pnas.1708274114)** — Nosek B.A.,
Ebersole C.R., DeHaven A.C., Mellor D.T., *PNAS*, **115**(11), 2600–2606, 2018. Разделение
postdiction и prediction: план с критерием фиксируется **до** наблюдения данных, иначе вывод
теряет ценность. Для регистрации отклонения плана нужна отдельная запись.

**Как это у нас.** §6b: `preregistered: true` ставится только если план с критерием закоммичен
**до** старта, а в `notes` — хеш коммита. Три требования:
1. вопрос и критерий (что считается положительным/отрицательным) — в `reports/` до запуска;
2. состав плеч и число сидов — до запуска, без «добавим потом»;
3. хеш коммита плана — в карточке; без хеша `preregistered` = `unknown`, а не «примерно true».

**Чего не даёт:** стандарта полей для вычислительных экспериментов; OSF подходит как формат
хранения, но ALife-специфичных шаблонов нет.
